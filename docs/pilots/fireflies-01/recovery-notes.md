# Recovery record

The first producer request completed. The initial runner then stopped between commissioning and research without recording its local exception. An ended process left a lease. After confirming that process had exited and the saved response ID existed, the stale lease was released explicitly. The next invocation retrieved the same producer response and continued; it did not submit a second producer request. The original interruption cause is unconfirmed. The runner now records sanitized local exceptions.

The first source read returned one completed exact-page open plus an empty `searching` open-page item without a URL. The response was completed and echoed `max_tool_calls=1`. The original parser counted both items and held the result for exceeding the configured tool maximum. No source-reading artifact was accepted at that point.

Official Responses documentation says calls beyond `max_tool_calls` are ignored: https://developers.openai.com/api/reference/python/resources/responses/methods/retrieve . The empty unfinished item is inferred to be such an ignored attempt; the documentation does not explicitly describe this exact returned shape. The parser now excludes only an empty, recognized nonterminal action when a completed response echoes its configured limit and exactly that many terminal tool actions are present. It separately records `ignoredWebAttempts`. Actions with payloads, completed extra actions, absent limit echoes and unknown statuses still count and can hold the job. The regression test covers each case.

Explicit `--reconcile-step research.read:2:source-1` preserves the prior held job in `before-reconciliation.json`, keeps the same usage record, reservation, bounds and response ID, and retrieves the response using GET. Only a successfully revalidated saved response can clear its bound and produce the source artifact. No replacement submission, budget increase or upstream regeneration is authorized by this recovery.

Three diagnostic GET requests were made outside the runner HTTP journal: one checked the producer status, one inspected the held source action/output, and one checked the echoed tool limit. Their timestamps were not recorded. Include these separately when reporting retrieval counts; none initiated another generation request.


The same local interruption recurred immediately after evidence synthesis completed. The recorded exception was `attempt to write a readonly database`. The open SQLite connection could read its recently accepted state, while a newly opened connection saw the preceding pending response and a retained lease. Workspace synchronization can replace the database inode between asynchronous provider polls; this is the working diagnosis, supported by a regression that replaces the database inode while a lease exists. The local adapter now opens and closes a SQLite connection for each statement. The test saves and releases the original lease successfully after replacement, then claims it through a new adapter.

The ended synthesis process's lease was explicitly released after verifying the saved response ID and current step. The accepted in-memory snapshot is preserved in `before-storage-recovery.json`. Recovery retrieves the existing synthesis response; it does not submit another synthesis request. No production D1 or R2 behavior was changed by this local storage fix. Operation latency includes these retrieval and operator delays, so the report labels it observed operation latency rather than provider-only processing time.
