# Researched episode generation

The hosted MVP now uses `lib/episode-service.ts` rather than this Python prototype. It advances five-minute jobs through outline, one source-grounded web-search response, script, an optional single script repair, factual review, contextual ElevenLabs v4 dialogue sections (up to 1,800 characters each, with adjacent context and recent request IDs), and Worker-compatible CBR MP3 assembly. The saved dialogue plan pins the reviewed script, voices, model, and section ordering; existing per-turn jobs retain their original path. D1 keeps private artifacts and R2 keeps audio. See the repository README for current behavior and verification limits. The sections below document the retained local Python tools.

`src.episode_pipeline` provides an opt-in workflow using the OpenAI Responses API. Importing it makes no requests. Configure `OPENAI_API_KEY` and optionally `EPISODE_MODEL`; keep the key server-side. The default model is configurable rather than embedded into generated content. No `.env` file is read by this module. The request uses Responses `text.format: {type: "json_object"}` and the current `web_search` tool only for research. OpenAI documents JSON mode as supported in Responses alongside the preferred schema-constrained mode, and recommends `web_search` for new integrations; see [Responses create reference](https://developers.openai.com/api/reference/resources/responses/methods/create), [web search guide](https://developers.openai.com/api/docs/guides/tools-web-search), and [structured outputs guide](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses).

## Workflow and cost controls

An episode is created for exactly 15, 30, or 45 minutes. The workflow is intentionally staged: one compact outline call; one bounded web-search dossier call; writing one outlined segment per call; one factual audit returning only issues and minimal edits; then deterministic Python assembly of the speech script and per-turn audio asset plan. There is no extra model call for speech formatting. Outline durations must sum to the selected length, with about 130 words per minute allocated per segment. Each section is separately output-capped; accumulated spoken text is checked against the requested duration. Draft turns must cite valid dossier finding IDs, except recognizable host framing/thanks lines, and each finding must cite valid source IDs. Empty source lists, unsupported references, and empty turns fail closed. If the first question appears in the opening, the opening must contain at least 100 words before it. Review questions block speech planning until resolved, and minimal review replacements are applied to the final spoken turns. Audio assets preserve speaker, text, claim references, and delivery, with estimated seconds and a speaker voice requirement. The dossier, individual draft sections, review, and plan can be persisted by passing `state_path` to `EpisodePipeline`, which writes checkpoints after completed stages and sections for resumption.

Each completed call records response ID, model, token usage when supplied, cache status, and timestamp. A configurable maximum call count blocks further API calls; each request also caps output tokens. Cache keys include prompt version, model, stage, and exact input, so unchanged stages can be reused without another paid request. Cache files contain model results and metadata, never credentials. Cache should be stored in a private server directory protected by the host application's storage policy.

## Boundaries and next integration work

Research results must be checked for source quality and locators. Web search is enabled only for the dossier stage. The current generator returns structured JSON, but conversion to the existing `episode-v1` contract needs an explicit mapping of expert1–expert3 to the product's speaker keys and a verifier for source/claim/turn references. An empty model review is not proof of accuracy. A custom episode should pass automated structural and source checks or fail without delivery; pre-recorded recommendations should receive human editorial review before publication. The app should describe custom output as AI-generated with inspectable sources, not promise perfect factual accuracy.

`src.elevenlabs_tts.ElevenLabsTTS` is an opt-in server-side provider adapter for `speech_plan.audio_assets`. It reads `ELEVENLABS_API_KEY` at construction (or accepts a key from server configuration), requires voice IDs for `host`, `expert1`, `expert2`, and `expert3`, preflights the entire plan against a configurable character budget and per-request character ceiling, and saves individual MP3 clips plus `tts_manifest.json`. The default call is `POST /v1/text-to-speech/{voice_id}?output_format=mp3_44100_128` with `xi-api-key`, JSON `{text, model_id}`, and `eleven_multilingual_v2`. ElevenLabs documents audio bytes as the successful response and `request-id`/`character-cost` response headers for metadata; see [Create speech](https://elevenlabs.io/docs/api-reference/text-to-speech/convert) and [API introduction](https://elevenlabs.io/docs/api-reference/introduction).

The adapter checkpoints `tts_progress.json` after each saved clip. Each turn record stores a SHA-256 over its exact text, speaker, voice ID, model, and format; a rerun reuses only matching valid MP3 clips and rejects changed inputs. The progress file contains no API key. The adapter retries explicit HTTP 429 throttles only (bounded, honoring `Retry-After`); it does not retry timeouts or other server errors because the synchronous POST API does not document an idempotency key, so the result of a failed request may be ambiguous and a retry could incur duplicate cost. A `seed` is not an idempotency mechanism. The configured per-request ceiling is a local guardrail, not a claim about the provider's universal hard limit. No default voice IDs are selected. `assemble_mp3_manifest()` reads the adapter manifest in order, joins local MP3 clips with FFmpeg, and verifies a non-empty positive-duration output with FFprobe. This helper does not add inter-turn pauses. No credentials, voice licensing, or paid live calls are part of the tests.

This module is a library, not an HTTP service. A production server should authenticate callers, apply per-user quotas, protect state/cache storage, and keep API keys out of browser code and logs. No live API call is required to run its tests.
